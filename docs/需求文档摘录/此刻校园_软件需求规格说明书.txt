1 引言
1.1 编写目的
本文档用于明确“此刻校园”软件系统的业务目标、用户需求、功能需求、数据需求、性能需求、运行环境及验收标准，为后续概要设计、详细设计、编码实现和测试提供统一依据。预期读者包括项目组成员、项目指导教师、测试人员、系统维护人员以及参与项目验收的相关人员。本文档同时作为需求变更和版本迭代的基准文件。
1.2 背景
项目名称为“此刻校园”，定位为面向高校校园生活的信息共享与生活地图系统。根据演示视频，系统以校园地图为核心载体，将校园中的生活信息、活动信息、二手交易、失物招领及其他校园信息进行位置化组织；用户可以在地图上查看信息，也可以通过搜索、分类和发布等方式获取或贡献内容。演示场景以江南大学校园为主要展示环境。
现有校园信息往往分散在班级群、学院群、社团群、公告栏及临时聊天消息中，信息具有时效性强、位置分散、难以检索和容易错过等特点。视频中以“找不到需要的信息”“错过活动”等场景呈现这一问题，并进一步展示了将信息绑定到地图位置、按类别组织、AI辅助搜索和发布、协同验证以及自动过期治理等解决思路。
本系统拟通过“地图驱动+信息留存+校园互助”的方式，把原本分散的信息沉淀为可检索、可定位、可互动的校园信息节点，从而形成围绕校园空间的信息共享闭环。

2 任务概述
2.1 项目概述
2.1.1 项目来源及背景
本项目为课程/项目组自主设计的软件系统。项目以高校校园生活中的信息分散、检索困难、位置关联不足以及信息生命周期管理不足为主要问题域，结合演示视频中“校园生活地图”“AI搜索”“AI辅助发布”“协同验证”“信息治理”等设计形成需求。
2.1.2 项目目标
建立以校园地图为核心的信息组织方式，使校园信息能够与具体地点建立关联。
提供分享吐槽、组队交友、二手交易、失物招领、其他等分类，形成统一的信息入口。
提供关键词搜索与AI智能搜索，支持用户用自然语言描述需求并获得相关信息。
通过AI辅助发布降低信息发布门槛，并支持用户手动修改AI建议。
建立评论、互动、举报和协同验证机制，提升信息的可确认性和可追踪性。
通过有效期和定时任务自动处理过期帖子，降低无效信息持续传播。
提供后台内容审核、用户管理、举报管理、地点核验、分类管理、专题管理、任务记录、操作日志及数据分析能力。
2.1.3 系统概述
系统主要面向校园普通用户和平台管理员。普通用户通过首页、地图、搜索、消息/互动及个人中心使用平台；管理员通过管理后台维护分类、审核内容、处理举报、管理地点及查看运行数据。
总体业务流程建议绘制为：
用户进入系统 → 浏览/定位校园地图 → 按分类查看信息节点 → 查看详情 → 评论/互动/验证/举报；
用户发布信息 → 输入标题、内容、图片及地点 → AI分析并给出分类/标签/有效期建议 → 用户确认或手动修改 → 发布 → 信息进入展示与互动流程 → 到期自动处理；
用户搜索 → 输入关键词或自然语言 → 系统识别搜索意图 → 检索分类、地点、标题、正文等信息 → 按相关性返回结果 → 查看详情并进行后续操作；
管理员进入后台 → 内容审核/举报处理/用户管理/分类管理/地点核验 → 记录操作日志 → 对异常、违规或过期信息进行治理。

2.3 假定和约束
项目演示以江南大学校园为主要场景，正式部署时需要配置对应学校的校园地图、地点及信息规则。
地图服务、AI服务、账号体系等外部能力的可用性会影响系统部分功能。
用户发布内容应遵守学校管理规定及相关法律法规；平台需要提供举报、审核、敏感信息处理等机制。
项目开发周期受课程进度约束，按照立项思路要求在第13周进行项目验收。
实际成本、服务器规格、第三方接口费用及最终技术栈需要在技术方案确定后进一步核算。

3.2 功能描述
3.2.1 F1 校园地图与信息浏览
功能定义：以校园地图为主要展示界面，将不同类别的信息以地图标记或信息节点形式呈现。用户可通过类别筛选、点击地图标记和地点聚合查看相关信息。
输入：地图范围、当前位置、分类筛选条件、地点选择。
处理：加载地图数据；查询指定范围的信息节点；按分类过滤；按照地点聚合信息；返回信息摘要。
输出：地图、信息标记、同地点信息列表及详情入口。
异常：地图服务不可用时提示；信息节点加载失败时允许重试。
3.2.2 F2 信息搜索
功能定义：支持普通搜索和AI智能搜索。普通搜索根据关键词匹配信息；AI搜索用于解析用户自然语言需求并结合分类、地点、时间等条件进行检索。
输入：关键词或自然语言描述。
处理：意图解析→条件提取→信息检索→相关性排序→结果生成。
输出：相关信息列表，并展示匹配原因/相关性等辅助信息。
异常：无法理解的自然语言输入应降级为关键词搜索或提示用户补充条件。
3.2.3 F3 信息发布
功能定义：用户可发布校园信息。演示中包括标题、分类、内容、地点和有效期等信息，并由AI辅助生成分类、标签、有效期等建议，用户可以手动修改。
输入：标题、正文、图片/附件（如支持）、分类、地点、有效期、联系方式。
处理：内容校验→AI辅助分析→生成建议→用户确认/修改→提交审核或发布。
输出：已发布的信息节点及帖子详情。
约束：发布内容需遵守平台规则；敏感联系方式等隐私信息应进行提示或保护。
3.2.4 F4 互动与协同验证
功能定义：用户可对信息进行评论、互动、验证和反馈，形成用户参与的信息确认机制。
评论：用户可对帖子发表文字评论。
协同验证：用户可对信息的真实性/有效性进行反馈，系统记录验证结果。
失物招领：支持拾得者发布信息、失主查看并按平台规则进行认领。
隐私控制：联系方式等敏感字段在展示时应有明确提示和必要保护。
3.2.5 F5 信息治理
功能定义：对平台中的违规、敏感、无效和过期信息进行生命周期管理。
举报：用户提交举报原因及相关说明，系统生成举报记录。
审核：管理员查看待审核内容并进行处理，记录处理结果。
过期治理：帖子设置有效期，到期后由系统定时任务自动转为过期/不可见等状态。
敏感信息：发布阶段进行风险提示；后台提供相应的审核和处置能力。
操作留痕：重要管理动作形成操作日志。
3.2.6 F6 后台运营管理
功能定义：管理员通过后台对平台基础数据和运营过程进行统一管理。演示界面包含仪表盘、内容审核、用户管理、举报管理、地点核验、分类管理、专题管理、任务记录、操作日志、用量与套餐、数据分析、系统设置等入口。
分类管理：新增、编辑、启用/禁用分类，设置分类描述、有效期、排序等。
内容审核：查看内容、审核状态、处理违规或异常信息。
用户管理：查询用户基本信息、账号状态及相关行为。
举报管理：查看举报记录、处理举报并记录结果。
地点核验：维护校园地点和信息位置关联。
任务记录/操作日志：查看定时任务和后台操作记录。
数据分析：统计信息量、分类分布、互动等运营指标。

6.2 软件接口
系统可能涉及以下外部软件接口：地图服务接口，用于地图底图、地点/坐标等能力；AI模型接口，用于自然语言搜索和发布辅助；身份认证接口（如采用学校统一身份认证）；文件/图片存储接口（如系统支持图片上传）。具体接口协议、鉴权方式、调用频率和异常码应在概要设计阶段根据最终选型确定。
6.3 硬件接口
系统原则上采用Web应用形态，不依赖专用硬件。用户侧可通过PC浏览器或移动端浏览器访问；服务器侧需具备满足应用服务、数据库、地图和AI接口调用需求的计算与存储资源。若后续增加校园自助终端等设备，应另行定义硬件接口需求。

可靠性：关键业务操作应保证数据不因页面异常而产生明显丢失；后台任务可追踪。
安全性：账号、权限和后台管理操作应进行权限控制；对联系方式等敏感信息提供必要保护；支持举报和内容审核。
可维护性：分类、有效期等业务规则尽量配置化；核心模块保持清晰边界并记录日志。
可移植性：前端应适配常见桌面浏览器和移动端浏览器；地图、AI等外部服务采用接口封装，便于替换。
